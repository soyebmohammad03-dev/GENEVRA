# The Digital Organism

Module: `genevra.organism` (`genome.py`, `phenotype.py`, `controller.py`,
`sensors.py`, `memory.py`, `learning.py`, `metabolism.py`, `mutation.py`,
`reproduction.py`, `organism.py`).

`Organism` is a coordinator, not a container for logic: each concern below
is its own class, and `Organism` composes them. This is what lets the
evolution engine (Phase 3) evolve genomes without knowing anything about
sensing, memory, or learning internals — and what lets learning mechanisms
be swapped without touching the genome format.

## Genotype vs. phenotype

`Genome` (`genome.py`) is the organism's heritable information: four named
NumPy arrays — `controller_weights`, `metabolic_genes`, `mutation_genes`,
`learning_genes` — plus a `ControllerArchitecture` (fixed layer sizes,
not itself evolved yet). Genes are grouped by concern rather than one flat
vector so new gene groups (memory parameters, morphology, ...) can be
added later as new fields without reinterpreting existing ones.

`develop(genome) -> Phenotype` (`phenotype.py`) is a pure function — no
randomness, no hidden state — that builds a `Controller` from
`controller_weights` and structures the other gene groups into
`MetabolicParams`/`LearningParams`. `Phenotype` is never the source of
truth and is never mutated directly; it is rebuilt from the genome. This
genotype/phenotype separation matters because GENEVRA's research questions
include how the genotype-to-phenotype map itself affects evolvability
(redundant encodings, robustness to mutation, etc.) — that question is
unanswerable if genotype and phenotype are the same object.

## The controller

`Controller` (`controller.py`) is a one-hidden-layer feed-forward network,
plain NumPy, `tanh` hidden activation, linear output (logits over the
discrete action space). Small and cheap deliberately — GENEVRA needs to
run thousands of organisms on a laptop, not one large model. Weights come
from `Controller.from_weights(architecture, flat_weights)`, reshaping a
genome's flat `controller_weights` vector into `weight1`/`bias1`/
`weight2`/`bias2` — the genome format and the controller's parameter
format are the same array, just reshaped, so mutation operators never need
to know about network structure.

`Controller.output()` accepts an optional `weights_override` for the
output layer. This is how lifetime learning (below) substitutes
plasticity-adjusted output weights into a forward pass without the
controller needing to know learning exists.

## The A / B / C learning split

This is the load-bearing design decision in Phase 2, because "can learning
strategies themselves evolve?" is only an answerable question if these
three things are kept structurally distinct:

- **(A) Inherited controller parameters** — `genome.controller_weights`,
  and therefore `Controller.weight1/bias1/weight2/bias2`. Set once at
  `develop()`, never modified during a lifetime.
- **(B) Lifetime-learned state** — `LearningState.output_weight_delta`
  (`learning.py`), created fresh each lifetime by `LearningRule.init_state`
  and discarded when the organism dies. Never written back into the
  genome; an organism cannot inherit what it learned.
- **(C) Heritable control of *how* learning happens** —
  `LearningParams.learning_rate`, derived from `genome.learning_genes`.
  Evolution can change how fast/strongly an organism's lifetime learning
  adapts without touching (A) or (B) directly.

`LearningRule` (`learning.py`) is a `Protocol` with two implementations:
`NoLearning` (state exists and is threaded through every call, it simply
never changes — a baseline for comparing "no lifetime learning" against
evolved learning) and `HebbianLearning` (`delta += learning_rate *
outer(post, pre)` on the output layer only, clipped to stay bounded).
`Organism.act()` combines them: `hidden = controller.hidden(x)`;
`effective_weight2 = learning_rule.effective_weights(controller.weight2,
learning_state)`; `logits = controller.output(hidden,
weights_override=(effective_weight2, controller.bias2))`. Only the output
layer is plastic in this first implementation — a deliberate scope limit,
not the ceiling of what the interface supports (a future `LearningRule`
could adapt hidden-layer weights, use reward as its plasticity signal
instead of the action taken, or implement a genuinely different mechanism
— reinforcement learning, memory-gated adaptation, evolved plasticity
rules — behind the same three methods).

## Sensing, memory, and internal state

`SensorSystem.encode()` (`sensors.py`) turns an environment `Observation`
plus the organism's *own* proprioceptive state (current energy, last
action taken) into the flat vector the controller consumes. Proprioception
is generated by the organism itself, not the environment — it's
information about the organism, not the world, and is kept separate from
`Observation` to preserve the environment's observation boundary (see
`docs/environment.md`).

`MemorySystem` (`memory.py`) is a small internal vector, private to the
organism (the environment never reads or writes it), updated each step by
a fixed exponential moving average over a chunked projection of the
sensory input. Reset at the start of each lifetime. It is a placeholder
minimum-viable mechanism — not learned, not genome-encoded — explicitly
marked as such (`ponytail:` in the module docstring); a learned or
heritable memory update rule is future work.

## Metabolism

`Metabolism` (`metabolism.py`) holds an organism's mutable energy budget:
`apply_step(action, resource_gained)` deducts `cost_for(action) +
base_upkeep` and adds any resource gained. All four costs
(`move_cost`, `stay_cost`, `eat_cost`, `base_upkeep`) come from
`MetabolicParams`, itself derived from `genome.metabolic_genes` — heritable,
not hardcoded — so movement and survival create a real trade-off that can
differ between organisms/lineages, not an arbitrary global score with no
consequence.

## Mutation

`MutationOperator` (`mutation.py`) is a `Protocol`; `GaussianMutation` is
the one implementation. Per-element, it mutates with probability `rate` by
adding `Normal(0, sigma)` noise — and critically, `(rate, sigma)` are read
from `genome.mutation_genes`, the genome *being mutated*, not from a
global constant. This is what makes mutation rate itself heritable: two
genomes with identical weights but different `mutation_genes` will mutate
by different amounts under the same RNG
(`tests/test_mutation.py::test_mutation_rate_is_read_from_genome_not_hardcoded`).
`mutation_genes` mutate too, at a small fixed meta-rate
(`ponytail:`-marked in code as a deliberate simplification — a fully
heritable meta-mutation-rate is future work, not a permanent ceiling).

## Reproduction — stops at one organism

`ReproductionSystem` (`reproduction.py`) answers exactly two questions for
a single organism: `can_reproduce(metabolism)` (energy above a threshold)
and `reproduce(genome, metabolism, rng)` (mutate a copy of the parent
genome, deduct an energy cost from the parent). It does not decide *who*
reproduces, does not manage population size, and does not implement
selection or recombination — those are population-level concerns for
`genevra.evolution` (Phase 3), deliberately not built yet.

## Reproducibility

`Organism` takes its own `numpy.random.Generator`, used for stochastic
action sampling (`_sample_action`, a softmax + categorical draw over
controller logits). Combined with a `GridWorld` seeded via `reset(seed)`,
an organism's entire lifetime trajectory is reproducible from three
integers: the genome's RNG seed, the environment's seed, and the
organism's own RNG seed — checked directly in
`tests/test_organism_environment_integration.py`.
